# MessageNote

[![CI](https://github.com/jiangfire/messagenote/actions/workflows/ci.yml/badge.svg)](https://github.com/jiangfire/messagenote/actions/workflows/ci.yml)

聊天框式的**本地优先**笔记应用。

## 这个产品在赌什么

「把消息发到聊天软件里当笔记」之所以流行，不是因为聊天适合记笔记，而是因为它把
**记录的启动成本压到了零**：不用想标题、不用选目录、不用决定格式，敲完按回车就结束。

代价是聊天软件解决不了的：消息被淹没、无法标注、无法检索、无法导出。

所以这个项目的核心命题只有一句话：

> **输入端要像聊天一样零摩擦，输出端要像笔记一样能组织。**

围绕这句话，有三条不可动摇的设计原则：

1. **捕获时不做任何决策。** 全局快捷键唤起 → 打字 → 回车。不选频道、不打标签、
   不写标题。界面看起来像 Slack，但默认行为像「文件传输助手」。
2. **组织是事后的动作。** 打标签、检索，都发生在记录之后。
3. **常驻，而不是「打开」。** 关窗只是隐藏，托盘一直在，随时能写。

## 快速开始

需要 **Rust 1.87+**（用到了 `is_multiple_of` / `repeat_n`）、**Node 24**、**pnpm 12**。
Windows 上还需要 WebView2（Win10/11 自带）。

```bash
pnpm install
pnpm tauri dev      # 开发（会拉起 Vite + 编译 Rust + 打开窗口）
pnpm tauri build    # 打 Windows 安装包 (NSIS) —— 需要下面的签名密钥
```

首次 `cargo` 构建需要下载依赖树（Tauri 约 400 个 crate），之后全部走本地缓存。

#### `tauri build` 需要更新签名密钥

`tauri.conf.json` 里配了 `createUpdaterArtifacts: true` 和公钥，此时
**没有私钥构建会直接失败**（`A public key has been found, but no private key.`）：

```powershell
$env:TAURI_SIGNING_PRIVATE_KEY = Get-Content "$env:USERPROFILE\.tauri\messagenote.key" -Raw
# **必须显式设成空串。** 不设的话 tauri 会弹交互式密码提示 —— 在 CI 里
# 表现成 job 一直卡到超时，而日志最后一行只是 "expect a prompt for password"
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = ""
pnpm tauri build
```

`pnpm tauri dev` 不需要它：dev 不打安装包。

新密钥用 `pnpm tauri signer generate -w <路径>` 生成，公钥换成
`tauri.conf.json` 里那一个（**换了公钥，已经在用户机器上的版本就再也收不到
你发的更新了** —— 它们会一律校验失败）。

### 开发环境注意事项

**关于国内镜像**：仓库里的 `.cargo/config.toml` 把 crates.io 指向了阿里云，
这是**有意提交**的，方便国内开发。GitHub 的 runner 在美国，所以 CI 里会先把它
删掉改用官方源 —— 绕那一圈既慢，又多一个第三方故障点。

在**受限沙箱**（例如 DSH 的 workspace-write 模式）里构建时有两个坑：

- 沙箱禁止写入 `~/.cargo`，而 cargo 必须往那里写。解决方式是把 `CARGO_HOME`
  临时指向工作区内：

  ```powershell
  $env:CARGO_HOME = "D:\codes\messagenote\.cargo"
  cargo build --offline
  ```

  代价是这份缓存不和系统共享（约几百 MB），所以在**普通终端里不要这么做**。

- 沙箱会阻断 Windows 的 schannel（原生 TLS），导致 cargo / git / curl **完全无法联网**，
  而 Node 自带的 TLS 不受影响。因此依赖需要先在沙箱外 `cargo fetch` 一次。
  另外 Vite 在 Windows 上会 `execFile("net use")` 探测网络驱动器，同样会被沙箱的
  管道限制挡掉，所以 `pnpm dev` / `pnpm build` 在沙箱内跑不起来。

以上都只是**本机沙箱的限制，不是项目问题**，普通终端里不会遇到。

## 时间线

浏览是主要的信息找回方式，检索是补充。理由很直接：**你往往记不住自己写过什么，
所以不知道该搜什么**。往前翻才是符合直觉的动作，所以分页比检索优化更优先。

时间线用 **keyset 分页**，游标是 `(created_at, id)` 复合键 —— 单时间戳游标会在
`created_at < t` 这一步把**同一毫秒内的多条消息整批跳过**，于是往回翻会凭空少掉
一段记录，而且不报错。`id` 是 UUIDv7，字典序即时间序，天然就是第二排序键。
这条有专门的测试固化（5 条同毫秒消息必须不重不漏地翻完）。

滚动到距顶部 320px 就自动加载上一页，并在上方插入内容后**保持视觉位置不动**
（记的是"距底部的距离"，插入内容不会改变它，还原它画面就纹丝不动）。
顶部会显示已载入条数，让你知道"现在看到的是不是全部"。

## 捕获浮层

主入口不是主窗口，而是一个 680px 宽、置顶、无边框的**捕获浮层**（`capture.html`）。
它是整个产品最重要的界面，因为它承担了「零摩擦」这一半命题。

按 `Ctrl`+`Shift`+`Space` → 浮层出现在屏幕水平居中、垂直约 22% 处 → 打字 → 回车。
发送后浮层自动收起，焦点原样还给原来那个窗口 —— 全程不用碰鼠标，也不切换应用。

几个刻意的行为：

- **永远落收件箱。** 浮层没有任何"选择去向"的能力。一旦这里能选频道，
  捕获动作就重新带上了决策成本，这个浮层也就退化成一个难用的新建窗口。
- **失焦即收起。** 点别处就消失，不需要去够 `Esc`。实现上要挡住窗口刚显示时
  的"伪失焦"事件（`CAPTURE_FOCUS_GRACE_MS`），否则浮层会一闪而过 ——
  这是自绘置顶窗口最经典的坑。
- **`Esc` 保留草稿。** 窗口是隐藏而不是销毁，半途收起的文字下次唤起还在。
  丢掉一个没写完的念头，比多留一行文字讨厌得多。
- **高度是量出来的，不是算出来的。** 输入框随内容长高，窗口跟着一起长；
  高度取面板的真实 `getBoundingClientRect()`，而不是把内边距、提示条高度
  硬编码成常量 —— 后者一旦改动 CSS 就会出现窗口与内容不匹配的缝隙。

### 为什么浮层是方的

浮层最初用的是 `transparent: true` + 圆角面板。实测发现屏幕合成结果里窗口四角是
纯黑，圆角会变成黑方块露在桌面上（本机 Windows『透明效果』是开启的，不是系统设置问题）。

更麻烦的是：**这个开发环境里两种截图手段都无法可信地判断透明是否生效** ——
`PrintWindow` 抓不到分层窗口的 alpha（把透明区域报成不透明纯黑），
而 `BitBlt` 系（`CopyFromScreen`）对 DWM / DirectComposition 合成的内容本就不保证正确。
Tauri v2 在 Windows 上走的正是 DirectComposition。

于是选了**能被验证**的那一边：窗口不透明，整块窗口就是面板本身，不留外边距、
不画圆角、不画外阴影，杜绝任何"露出底色方块"的可能；视觉上的"输入态"靠顶部
一条 accent 强调线表达。

想换回圆角的话改动很小（在 `tauri.conf.json` 的 capture 窗口加 `"transparent": true`，
并把 `capture.css` 里 `html,body` 的 background 改回 `transparent`、给 `.capture-shell`
加回 padding），但请**先在自己机器上亲眼确认**透明确实生效 —— 这正是我在这里
无法替你验证的那一步。

## 多设备同步

单用户、多设备。服务端只做一件事：**保存状态并分配一个单调递增的序号**。
所有合并逻辑在客户端，且客户端与服务端共用同一份裁定规则。

### 两条时间轴，各管一件事

这是整个同步设计里最要紧的一点：

- **`server_seq`（服务端分配的单调整数）** 回答"我上次同步之后，服务端有哪些变化"。
  用时间戳做游标的话，任何一台设备时钟偏慢，它写的数据就永远落在别的设备游标
  之前 —— **永久漏拉，而且不报错**。
- **HLC（混合逻辑时钟）** 回答"同一行两边都改了，谁赢"。

两者不能混用：拿 seq 判胜负会变成"网络顺序赢"，跨设备不一致；拿时间戳做游标会漏数据。

HLC 是 `(wall_ms, counter, device)` 三元组，按这个顺序全序比较。收到远端时间戳时
把本地时钟**拉前**到两者最大值，所以时钟偏差最多造成一次性影响，会被立刻校正，
不会永久积累。`device` 那一层是必需的：两台设备完全可能在同一毫秒各写一次，
不打破平局就会各自认为自己的版本胜出。

### 冲突策略（请知悉这条边界）

- **从未到达服务端的编辑，绝不丢失。** 推送被服务端拒绝时，本地那一版会被存成
  一条带「冲突副本」标签的新消息，然后才应用服务端的版本。
- **已经到达服务端的编辑，被更新版本覆盖时不留副本。** 那是 LWW 的正常语义，
  等同于你在一台设备上先后改两次。每次覆盖都留副本只会把库变成噪音场，
  反而让真正的冲突副本淹没其中。

两条策略各有一个测试固化。如果你需要更强的保证（"已同步过的编辑也不该被静默覆盖"），
那需要版本向量而不是单个 HLC —— 是明显更重的设计，目前没做。

### 四条不能违反的规则（都在代码里标了原因）

1. **墓碑时间由变更内容推导，不用本机 `now()`。** 否则两台设备对同一条墓碑写出
   不同的 `deleted_at`，状态永远收敛不了。
2. **清 `dirty` 必须带 HLC 条件。** 推送在途时用户又改了同一行，无条件清零会把
   那次修改误标成"已同步"，它再也不会被推出去。
3. **远端胜出而本地有未上传的改动时，先留副本再覆盖。** 个人记忆工具里，
   少一条笔记比多一条重复内容严重得多。
4. **网络往返期间绝不持有数据库锁。** 否则服务端不可达时，用户打字会卡住整个
   HTTP 往返（连接超时 4 秒、整体兜底 30 秒），而且不会报任何错。这条由类型
   保证：`sync_once` 只接受 `LocalStore`，拿不到 `&Connection`。
   详见 [ROADMAP 第五节](ROADMAP.md)。

另外一条不算"规则"但同样重要：**检索索引是派生数据，从不参与同步**，各端本地重建。

### 同步期间界面照常可用

网络往返（连接超时 4 秒、整体兜底 30 秒）全程**不持有数据库锁**，所以服务端
不可达时你照样能打字、能检索、能翻时间线。

代价是同步不再是"一个原子的整体"，而变成了**读一批 → 走网络 → 写一批**。
中间用户产生的新编辑靠 HLC 条件被识别出来（清 `dirty` 时会比对 HLC，
对不上说明这行在推送在途时又被改过），留给下一轮推送 —— 不会丢。
拉取那边同理：落库和推进游标在同一次加锁里完成，万一崩在中间，
下次重拉同一批会走 HLC 相等那条幂等路径。

## 部署服务端

**最省事的方式是一条 `docker compose up -d`** —— 完整步骤、TLS、备份、
以及"反代必须关掉响应缓冲否则实时推送不工作"那个坑，见
[`deploy/README.md`](deploy/README.md)。下面是裸机方式。

服务端**只说 HTTP 明文、且默认只绑 `127.0.0.1`** —— TLS 交给前面的反向代理。
默认绑 `0.0.0.0` 会让人一不留神就把装着全部笔记的明文端口暴露到公网。

```bash
cargo build --release -p messagenote-server
# 生成令牌
export MESSAGENOTE_TOKEN=$(openssl rand -base64 48)
MESSAGENOTE_DB=/var/lib/messagenote/server.sqlite ./messagenote-server
```

三个环境变量：`MESSAGENOTE_TOKEN`（**至少 32 字符**，启动时强制检查）、
`MESSAGENOTE_DB`、`MESSAGENOTE_BIND`。

附件字节默认和笔记一起躺在那个 `.sqlite` 里。图多了想拆出去的话，设
`MESSAGENOTE_S3_BUCKET` 就能把字节放进 S3 兼容的对象存储（AWS / MinIO / R2 / B2）——
对象键就是附件的 sha256，所以天然去重。**切过去不需要先把老字节搬过去**
（读的时候会穿底查一次库），但**切回来要**：把桶里的对象倒回库里，
或者在切之前就把字节同步回去。变量清单、需要的桶权限和注意事项见
[`deploy/README.md`](deploy/README.md)。

`deploy/` 下有可以直接用的 `Caddyfile`、`systemd` unit 和 env 示例。
两点值得强调：

- **令牌是这个服务的唯一凭据**，公网上必然会被扫描。用 `openssl rand` 生成，
  并给反向代理装限流（官方 Caddy 不带 `rate_limit`，需要 `xcaddy` 编译插件，
  Caddyfile 里写了具体做法）。
- **备份**：单台 VPS 的磁盘不是备份。用 [Litestream](https://github.com/benbjohnson/litestream)
  把 SQLite 持续复制到对象存储，恢复就是拉回一个文件。
  客户端虽然各有一份完整副本，但在网页端写入的内容只存在于服务端。

## 网页端

浏览器里能看、能搜、**也能记**。和桌面端跑的是同一套界面 —— 区别只在数据从
哪儿来（`NoteApi` 的两个实现：Tauri `invoke` vs HTTP）。

### 部署：必须和 API **同源**

服务端**不带任何 CORS 头**。把网页端放在和 `/api` 不同的域名下，浏览器会直接
拦掉所有请求 —— 所以用同一个域名：Caddy 既托管静态文件、又反代 `/api/*`。
[`deploy/Caddyfile`](deploy/Caddyfile) 里是现成的配置。

```bash
pnpm build
# 只拷网页端需要的那两样。
# **不要**拷 dist/index.html —— 那是 Tauri 主窗口的壳，依赖 window.__TAURI__，
# 在浏览器里打开只会白屏。
install -d /var/lib/messagenote/web
cp -r dist/assets dist/web.html /var/lib/messagenote/web/
```

打开页面，填**长期令牌**，登录一次。服务端地址已经默认填好了（就是页面自己的
origin）—— 同源部署下那个输入框本来就是多余的。

### 几点值得知道

- **长期令牌不会留在浏览器里。** 它只用来换一个**会话**；之后所有请求带的是
  会话。会话能过期、能吊销（`DELETE /api/session`）—— 这是相对"把长期令牌
  塞进 localStorage"的主要收益。
- **会话会在你用它的时候自动续期**，所以天天用的人不会被踢掉。会话该过期的是
  "不再使用的"，不是"用了很久的"。
- **万一真的过期了，你正在写的东西不会丢。** 重新登录是个浮层，界面不会卸载 ——
  下面那段没发出去的文字还在。
- **写入由服务端代笔。** 服务端以一台设备的身份生成 HLC、写进变更日志、分配 seq，
  桌面端下次同步照常拉到。所以浏览器里**没有第二套合并规则** —— 裁定权仍然
  只有 `core::merge` 那一份。
- **代价：网页端写入需要联网。** 浏览器里没有本地库，离线队列留给 S3。
- **没有捕获快捷键和置顶浮层**（浏览器里做不到）。所以网页端的重心是查和整理；
  真正的"随手记"仍然只有桌面端能做。

### 服务端 HTTP 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/health` | 存活探针，**不鉴权** |
| GET | `/api/sync/handshake` | 鉴权过的握手（桌面端"测试连接"用这个） |
| GET | `/api/sync/pull` | 拉取变更（`since` 游标） |
| POST | `/api/sync/push` | 推送变更 |
| POST | `/api/session` | 长期令牌换短期会话 |
| DELETE | `/api/session` | 退出登录 |
| GET | `/api/timeline` | 时间线（scope + 键集游标） |
| GET | `/api/timeline/stats` | 侧边栏那两个计数 |
| GET | `/api/channels` / `/api/tags` | |
| GET | `/api/search` | 检索 |
| POST | `/api/message` | 记一条 |
| PATCH / DELETE | `/api/message/{id}` | 改正文 / 删除 |
| POST | `/api/message/{id}/move` | 换频道 |
| PUT | `/api/message/{id}/tags` | 整体替换标签 |
| POST | `/api/channel` | 建频道 |
| PATCH / DELETE | `/api/channel/{id}` | 改名 / 删除（连同里面的消息） |

除 `/api/health` 和 `POST /api/session` 外，全部需要
`Authorization: Bearer <长期令牌或会话>`。读取和写入**都走 `crates/store`**，
和桌面端是同一份查询实现 —— 有测试逐字段比对两端的 JSON。

```
└──────────────┬──────────────────────┘
               │ ureq + rustls
┌──────────────▼──────────────────────┐
│─ 服务端 crates/server/ ─────────────│
│   axum 路由 (api.rs)                │
│        │                            │
│   服务端存储 (store.rs)              │
│        ──▶ SQLite + server_seq      │
└─────────────────────────────────────┘

共享内核 crates/core/：
  search（bigram 分词）· hlc · merge（谁赢的裁定）· wire/payload（协议）· models
```

Cargo workspace **四个**成员。**共享内核的取舍标准是"一旦两份实现分歧就会静默出错"**：
中文分词、HLC 比较、合并裁定、协议字段名都属于这类 —— 写读两端不一致就是检索
静默失效、状态永不收敛，而且都不会报错。

`crates/store` 是后加的一层，契约只有一句：**只放"在客户端与服务端两种 schema
上都成立"的查询**。浏览和检索属于这类（服务端的表是客户端同名表的超集），
写入不属于（客户端有 `dirty`，服务端有 `server_seq`）。这条前提有测试钉着
（`shared_browse_queries_work_on_the_server_schema`），不是读一遍 schema 的推断。

`core` 因此保持**纯逻辑、不依赖 rusqlite**。`clock`（HLC 推进）和 `normalize`
（内容校验）也在 `store` 里 —— 这两段各写一份必然分叉：前者决定"谁更新"，
后者决定"什么算合法输入"。

**Rust 独占数据库，前端不碰 SQL。** 前端只通过 `src/lib/api.ts` 那层类型化封装
调用命令。中文检索需要在 Rust 侧对正文做预处理，如果让前端直接写 SQL，
索引会和写入逻辑脱钩，而索引不同步是一种**静默失效**——搜不到，但不报错。

### 组织方式：时间线 + 频道 + 标签

三个概念的**分工是明确的**，这是这套设计唯一需要记住的一句话：

- **频道管归属（互斥）** —— 一条记录属于且仅属于一个频道。这是主要的整理动作。
- **标签管横切（可多个）** —— 与频道正交。归档到 `#项目A` 的记录照样可以带 `#重要`。
- **时间线是唯一的浏览面** —— 全部记录，可以一直往前翻。

侧边栏长这样：

```
时间线      13        ← 唯一的浏览面
频道        +
  # 项目A    0        ← 归档目标
标签
  重要  待办          ← 横切标记
```

而**时间线上方有一条筛选**：`[全部 13] [未归档 3] ｜ 时间：[不限] [今天] [近 7 天] [近 30 天]`。
时间档位在客户端折算成一个绝对的 `since` 时刻（epoch 毫秒）下推到查询层
（`list_messages`）——「今天」这种本地日历语义只有客户端说得清，SQL 只看毫秒。

主窗口输入框的**去向跟随当前视图**：在 `#项目A` 里发就进 `#项目A`，输入框下方的
「发送到」如实标注去向。捕获浮层的零摩擦路径**不受影响** —— 它没有上下文，
依旧永远落收件箱（见上一节）；两条路径互不绑架。

每条消息带一个头像。**点它可以换成自己上传的图**，悬停时右上角出现清除按钮。
字节复用现有的附件存储（桌面端 SQLite、网页端服务端），只有 64 字符的 sha 存
localStorage —— 和字号档位同一个位置，两端各记各的。没有自定义头像时显示「我」：
那个字符不是占位符，它在纯文字流里承担"这是对话不是日志"的视觉作用。

头像**不参与同步**。它描述的是"这台机器屏幕里那个圆圈长什么样"，不是笔记数据 ——
换台机器重新设一次是对的。

顶栏右侧有字号档位（小 / 标准 / 大 / 特大）：全部字号用 rem 表达，档位写进根元素的
`--font-scale`，一处生效全局跟随，localStorage 持久化（桌面端与网页端各自记忆）。

**收件箱不作为导航项出现**，它就是那条「未归档」筛选 —— 也就是 `channel_id` 还停在
默认落点、没被归档的那些。捕获永远落到那里，所以"收件箱"表达的是一个**状态**
（还没归档），而不是和频道平级的第二个分类。

> **为什么不是「收件箱 = 未打标签」**
>
> 这个版本短暂存在过，是错的：它让"未打标签"和"未归档"绑在一起，于是只要你
> 不怎么打标签，收件箱和时间线的数字就几乎一样，两个入口看起来就是同一个视图
> 重复了两遍。**归属归频道管，标记归标签管** —— 两者不该互相绑架。

顺带一提，如果侧边栏同时列出「未归档 6」和「📥 收件箱 6」，那又是同一个东西重复
两遍。所以收件箱不进频道列表，只在消息的「归档到」菜单里作为可选项出现（用来把
东西移回去）。

### 数据模型

- `channel` —— 频道。`kind = 'inbox'` 的 ID 固定为 `inbox`，是**每台设备各自创建的
  常量实体**（时间戳写死 0、`dirty` 恒为 0），所以它不参与同步也不会产生任何冲突。
- `message` —— 一条记录（= 一条消息）。`channel_id` 决定它归在哪个频道。
- `tag` —— 标签，**以标签名为主键**。身份本来就是它的名字，两端天然一致，
  不需要哈希也不需要额外约束。代价是重命名等价于"旧的消失 + 新的出现"。
- `message_tag` —— 消息与标签的关联，**刻意不加外键**：同步批次里一条关联可能
  先于它引用的标签到达，外键会让整批回滚。
- `message_fts` —— FTS5 虚拟表（仅客户端）。派生数据，从不参与同步。
- `meta` —— 键值表：`device_id`、`hlc_wall`/`hlc_counter`（时钟状态）、
  `sync_url`/`sync_token`、`sync_cursor`。

每个可同步实体都带：`device_id`、`hlc_wall`、`hlc_counter`、`deleted_at`、`dirty`。

删除一律是软删除。同步需要区分「这条被删了」和「这条还没同步过来」—— 少了墓碑
这两件事无法区分，删除会像幽灵一样在别的设备上复活。


### 中文检索：为什么不用 FTS5 自带的方案

这是整个项目技术上最要紧的一处取舍。

- FTS5 自带的 **`unicode61`** 分词器按字母/数字边界切词。中文没有空格，**整句会变成
  一个 token**，任何子串查询都匹配不到 —— 中文检索直接失效。
- FTS5 自带的 **`trigram`** 分词器能救一部分，但它要求查询串**至少 3 个字符**，
  而中文里最高频的查询恰恰是「笔记」「会议」这类**双字词**。所以也不够。

**采用的方案**：写入索引前，把连续的 CJK 段切成重叠的**二元组（bigram）**：

```
今天开会讨论  ->  今天 天开 开会 会讨 讨论
```

查询时用同样的规则切分。于是双字词就是一个精确 token，多字词变成若干个必须同时
出现的 token（AND 语义）。标点会切断 CJK 段，所以「拿起了笔，记下」不会产生
「笔记」这个 bigram。零第三方依赖，也不需要自定义 SQLite 分词器扩展。

bigram 天然会有跨词边界的假阳性，所以检索的最后一步**一定**用原始子串做精确过滤，
保证「搜得到的，一定是真的包含」。

**已知边界**：这是**连续子串**匹配，不是分词匹配。原文写「开了个会」时搜「开会」
是搜不到的（中间隔着「了个」）。这条语义有专门的测试固化，避免以后被误当成 bug
「修」坏。真正的解法是后续接入中文分词或语义检索，而不是放宽匹配。

单字 CJK 查询（如只输入「记」）无法构成 bigram，会退化为 `LIKE` 扫描。

### 安全性

笔记正文会被渲染成 Markdown 并 `dangerouslySetInnerHTML` 进 WebView。**粘贴**进来的
内容可能夹带脚本，在桌面应用里这等价于本地代码执行，所以渲染前必须过 DOMPurify。

## 测试

```bash
cargo test --workspace
```

测试覆盖的是**行为**，不是实现细节。四个层次：

**共享内核 `crates/core`** —— HLC 的单调性与时钟回拨、同毫秒/同 wall 的确定性打破
平局；合并裁定的六种情形（本地没有 / 重复投递幂等 / 远端更新 / 本地更新 /
有未上传改动要留副本 / 内容相同不留副本）；bigram 分词、跨标点边界、单字回退。

**客户端存储 `src-tauri/src/db.rs`** —— FTS5 确实被编译进来、中文双字词检索、
跨词边界假阳性被精确过滤、「连续子串而非分词」这条语义边界、软删除、改正文后
索引重建、标签以名字为身份、孤儿标签**不再**被回收、写操作置 `dirty` 并推进 HLC、
以及**拿一份真实的旧库副本跑 v1 → v2 迁移**。

**同步引擎 `src-tauri/src/sync.rs`** —— 对着内存假服务端跑：单设备推送对端全量拉取、
重复推送幂等、长期离线后收敛、被拒编辑留副本、已接受编辑不留副本，以及
**150 步随机操作后两台设备逐字节一致**（快照包含 `deleted_at`、HLC、`device_id`）。

这里还有一对**守卫测试**，守的是"网络往返期间不持有数据库锁"：假服务端在每次
"net 调用"里反过来去申请数据库锁，锁被占住就直接红。另一条测试专门验证那个探针
本身有效 —— 没有它，守卫测试可能因为探针失灵而永远绿。

**后台工作线程 `src-tauri/src/sync_worker.rs`** —— 跑的是应用真正走的那条路径
（`sync_with`），对着一个进程内的真实 axum 服务端。其中一条用"接得上但永不回话"
的 TCP 服务端制造稳定的网络在途窗口，确认那段时间里数据库仍然打得开。
所有等待都用 `recv_timeout` 而不是 `join()`：真出现死锁时要是挂住，
会被当成"跑得慢"而不是失败。

**真实 HTTP 端到端 `src-tauri/tests/sync_e2e.rs`** —— 在一个进程里把**真实的**
axum 服务端跑起来（绑临时端口），两个真实客户端库通过真实 `ureq` 同步。
这一层专门抓单元测试抓不到的东西：字段名少一个、大小写差一点，
单测全绿而实机全挂。

```bash
# 用一份真实的旧库副本验证迁移（默认被 ignore）
$env:MESSAGENOTE_MIGRATE_TEST_DB = "…\副本.sqlite"
cargo test -p messagenote -- --ignored --nocapture
```

## 当前限制（v1.8.0）

诚实地列出来，避免误判成熟度：

- **离线只覆盖「记一笔」，不覆盖浏览。** 浏览器里没有本地库（刻意**不**重建
  sqlite-wasm + OPFS）：断网时能捕获文字，但浏览、检索、归档都要联网 ——
  网页端**写入本身也需要联网**，离线队列负责的只是捕获那一段。
  队列**只收文字**：断网时粘图片会走 `saveAttachment` 的失败路径，
  这是有意划的边界，不是遗漏（见 ROADMAP 的 S3 阶段，即"离线捕获"那一节 ——
  和下面那条"附件放对象存储"是两回事，只是撞了同一个缩写）。
- **网页端没有捕获快捷键和置顶浮层。** 这两样在浏览器里都不存在，所以网页端
  的重心是查和整理，写入够用即可。真正的"随手记"仍然只有桌面端能做。
- **导出在两端形态不同。** 桌面端写一棵目录树（挑一个目录，能直接进版本控制）；
  网页端下载一个 `.zip`（浏览器里写不出目录树）。**内容是同一套渲染和筛选**，
  所以两端导出的东西对得上。
- **附件只支持图片内联展示**（png/jpeg/gif/webp）。其它类型能存能传，但只当下载，
  不会渲染 —— 一个声明成 `text/html` 的上传文件在同源部署下就是存储型 XSS，
  所以类型只由字节嗅探决定，绝不采信请求方声明的 Content-Type。
- **附件字节默认存在数据库里**，库文件会随图片增长。这是**故意的**：备份工具
  （Litestream）只跟一个 `.sqlite` 文件走，图片放外面会被静默漏掉。
  不想这样可以在服务端设 `MESSAGENOTE_S3_BUCKET`，把字节交给对象存储
  （桌面端的本地库不受影响，它永远是本地的）。
  不再被引用的字节要手动回收 —— 桌面端 ⋯ 菜单里的「维护 → 回收没被引用的附件…」。
- **对象存储那条路只能往一个方向平滑走。** 切到 S3 不用先搬字节（读的时候会
  穿底查一次库），但**切回 SQLite 要手工把桶里的对象倒回去** —— 撤掉桶名之后，
  只有在 S3 期间传上去的图会取不到（库里没有它们）。没有做自动迁移，理由和
  做法见 [`deploy/README.md`](deploy/README.md)。
- **外链图片会向第三方暴露"你打开了这条笔记"。** WebView 的 CSP 是收紧过的
  （脚本注入那一层挡住了），但 `img-src` 刻意留着 `https:` —— 笔记里
  `![](https://…)` 能正常显示。哪天想换掉这个取舍，删掉 `img-src` 里的 `https:` 即可。
- **应用图标是程序生成的**（`scripts/gen-icon.mjs`，纯 Node 手写 PNG 编码），
  不是设计稿。要换图标就改那个脚本后重跑 `pnpm tauri icon scripts/app-icon.png`。
- **安装包未做代码签名。** Windows SmartScreen 会对未签名的安装程序弹警告 ——
  这是预期行为，不是安装包损坏。自用可以直接「仍要运行」。
- **`/api/health` 不鉴权**（故意的，给监控探活用），它只泄露"这里有个
  MessageNote 服务端"。需要确认令牌的场合请用 `/api/sync/handshake`。

## 导出

**笔记拿得出去。** 顶栏 ⋯ 菜单里的「导出记录…」（桌面端）：定好要导哪一部分
（**频道 / 标签 / 起止日期**，都是可选的，全不选就是全部），挑一个目录，
得到一棵 Markdown 目录树：

```
<你挑的目录>/
  项目A/
    2026-09-29-2103 会议记录：讨论下一步.md
  收件箱/
    2026-09-29-2103 地铁里随手记的一句.md
  attachments/
    9656be35bd35….png
```

每条记录是一个 `.md`，开头是 front-matter：

```markdown
---
channel: "项目A"
tags: ["待办", "重要"]
created: 2026-09-29T21:03:49+08:00
updated: 2026-09-29T21:03:49+08:00
---

会议记录：讨论下一步

![截图](../attachments/9656be35bd35….png)
```

几点值得知道：

- **文件名是 `<本地时间标签> <第一行摘要>.md`。** 按字典序排就是时间序，
  所以文件管理器里排一下就是时间线。
- **图片一起带走。** 正文里的 `attachment:<sha>` 重写成相对路径，在导出物里
  点开就能看。字节**直接从 SQLite 读出来写盘**，不经过界面。
- **同一条记录连导两次，结果逐字节一致** —— 所以导出物可以直接进 git。
- **单条复制**是每条记录右侧那个 ⧉ 按钮。桌面端复制的是**渲染过的 Markdown**
  （带上面那段 front-matter），和全量导出走同一个渲染器，所以两处不会长得不一样。
  **图片会内联成 data URI** —— 剪贴板里没有"文件"这个概念，只有文本；
  内联之后复制出去贴到任何能画 Markdown 的地方（GitHub、Obsidian、LLM 对话框），
  图都还在。（全量导出那边不同：它有磁盘可用，写相对路径、图单独成文件，
  产物因此是可读、可 diff 的文本。）
- **取不到的附件会被说出来。** 某张图本地还没有字节时（对端还没传上来），
  导出完成会告诉你"有 N 个附件没有带出来"，正文里保留 `attachment:<sha>` 引用 ——
  等同步把它们拿下来再导一次即可。
- **可以只导一部分。** 频道、标签、时间范围三个筛选任意组合：
  只导某个项目频道的全部记录、只导打了「周报」标签的、或者只要 3 月 1 日到
  3 月 31 日这一段的。**两个日期都算在内**（含当天 00:00 到 23:59:59.999），
  日期按**本机时区**折算成绝对时刻 —— 和文件名那套用的是同一个口径。
  这个时间范围和**时间线**上那个「今天 / 近 7 天」不是一回事：档位回答的是
  "我最近记了什么"，只给一个下界；导出要的是一个**区间**（写周报、交存档
  常常要"某月到某月"）。
- **两端形态不同，内容是同一套。** 桌面端挑一个目录、写出一棵 Markdown 目录树；
  网页端（顶栏 ⋯ 里的「导出记录…」）下载一个 `.zip`，里面是同一棵目录树 ——
  浏览器里写不出目录树，但 zip 能装下它。**筛选和渲染走的是同一份代码**，
  所以两端导出的东西对得上，不存在"网页端导一版、桌面端导另一版"。

## AI 标签建议

**AI 只做一件事：建议标签。而且是"建议态" —— 虚线 chip，点一下才真的打上。**

在每条记录下面点「＋ AI 建议标签」，它会把正文交给一个 OpenAI 兼容端点，
回来几个标签建议。**猜错了不会有任何损失**，因为它们只是几个还没生效的 chip。

这是刻意的边界。AI 直接写标签听着更省事，但猜错的那条会静悄悄混进你的标签
体系 —— 而标签是要拿来搜的，污染它等于慢慢毁掉检索。所以 AI 不写入、不改写、
不总结。

三点值得知道：

- **在哪配。** ⋯ 菜单 →「AI 设置」，填**接口地址**（Base URL）、**API Key**、
  **模型名**。云 API 和本地模型（Ollama / LM Studio / vLLM）都吃 OpenAI 兼容
  协议，一层就够。**api_key 存在本机库里，跟着备份走，但不同步** ——
  它不该在设备之间来回传。
- **建议会落库，而且稳定。** 同一个 id 重跑不会凭空换一批建议 ——
  「每次重跑结果都变」的功能，用第三次就没法信了。
- **按钮恒显，不按"配没配好"隐藏。** 没配或调不通时，它会直接告诉你缺什么、
  该去哪配。

## 下载

预编译产物在 [Releases](https://github.com/jiangfire/messagenote/releases)：

| 文件 | 说明 |
| --- | --- |
| `MessageNote_<版本>_x64-setup.exe` | Windows 桌面端安装包 |
| `MessageNote_<版本>_x64-portable.exe` | Windows 免安装版，双击即用 |
| `messagenote-server_<版本>_windows-x64.exe` | 同步服务端（Windows） |
| `messagenote-server_<版本>_linux-x64` | 同步服务端（Linux，glibc） |
| `messagenote-server_<版本>_linux-x64-static` | 同步服务端（Linux，**静态**，任何发行版都能跑） |
| `SHA256SUMS.txt` | 上面这些文件的校验值 |
| `latest.json` | 桌面端自动更新的清单（**不用手动下**） |

安装包**未做代码签名**，Windows SmartScreen 会弹警告 —— 这是预期行为，
不是安装包损坏。自用可以直接「仍要运行」。

### 校验下载没被篡改

```bash
sha256sum -c SHA256SUMS.txt
# Windows:
certutil -hashfile MessageNote_<版本>_x64-setup.exe SHA256
```

校验值**替代不了代码签名**：它证明不了"这是作者发的"，但能证明"下载过程中
没被人改过"。注意它和更新签名是两回事 —— 后者保护的是自动更新链路，
用的是 Tauri 自己的密钥对。

### 自动更新

桌面端**每次启动会自动查新版本**，有的话在顶栏显示一条提示，点一下就更新并重启。
**刻意不做静默自动更新**：装新版本要重启，而用户可能正在写东西 ——
捕获浮层里那段还没发出去的草稿只在内存里（窗口是隐藏而不是销毁，所以它才留得住），
一重启就没了。拿一段可能正在写的笔记去换一个后台升级，不划算。

更新包会**校验签名**之后才安装。这一条不能省：更新包是从网上拿的，
不校验就等于让任何人给你换一个 exe。公钥在 `src-tauri/tauri.conf.json` 里。

> **自动更新只能从"第一个带它的版本"开始。** 更新是客户端主动去查的 ——
> 一个本身不含更新插件的老版本，不会因为你发了新版就突然会升级。
> 在自动更新上线之前发布的版本需要**手动装一次**新版本，之后才是自动的。

### 用容器自建服务端

```bash
cp deploy/.env.example deploy/.env   # 填一个至少 32 字符的令牌
docker compose --env-file deploy/.env up -d
```

一条命令起一个完整的 MessageNote（服务端 + 网页端，只暴露一个端口）。
细节、TLS、备份、以及"反代必须关掉响应缓冲"那个坑，见
[`deploy/README.md`](deploy/README.md)。
