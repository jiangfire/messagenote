# 服务端 S3 附件后端的端到端验证

[`scripts/desktop-verify/`](../desktop-verify/README.md) 验的是桌面端，
[`scripts/web-e2e/`](../web-e2e/README.md) 验的是网页端。这里验的是**服务端把
附件字节放进对象存储**那条路（`crates/server/src/blobs.rs`）。

## 为什么需要它

`crates/server` 里的单元测试用的是 `object_store` 自带的 `InMemory` 实现 ——
它和 S3 共享同一段代码路径，所以**逻辑**是验到了的。验不到的是协议那一层：

- **签名（SigV4）到底算不算得对**，端点、桶名、区域拼出来的 URL 长什么样；
- **路径式寻址**（`/bucket/key`）和虚拟主机式（`bucket.host/key`）的区别 ——
  自建对象存储（MinIO / R2 / B2）基本都要路径式，而这件事**没有单元测试能发现**：
  内置的 `InMemory` 根本不发 HTTP。

所以这里对着一个**真的 S3 协议实现**跑：用 [moto](https://github.com/getmoto/moto)
在本机起一个 S3 服务，服务端二进制用 `MESSAGENOTE_S3_*` 指向它。

## 怎么跑

```powershell
python -m pip install "moto[s3,server]"   # 一次性
cargo build -p messagenote-server
pwsh -NoProfile -File scripts/s3-e2e/run.ps1
```

产物（服务端日志、临时库）落在 `.scratch/s3-e2e/`（gitignore 的临时区）。
脚本只停自己起的两个进程。

## 它断言了什么

19 条，从"字节真的进了桶"到"老数据还取得到"：

| 验的 | 为什么值得单独一条 |
| --- | --- |
| 上传后桶里正好一个对象，键是 `attachments/<sha256>` | 键算错的话，去重和"客户端取得到"会同时悄悄失效 |
| 同样的字节再传一次，桶里还是一个对象 | 内容寻址的去重是**对象存储这一侧的**性质，不是接口层的 |
| 下载的字节与上传的逐字节一致，`Content-Type` 是嗅探出来的 | 声明的 `text/html` 不能影响任何东西（存储型 XSS 那条规矩） |
| `missing` 只报真的没有的 | 客户端靠它决定传哪些；报错方向会让它反复重传 |
| 手工往 SQLite 塞一份"老字节"，HTTP 上仍取得到、且**不算缺** | 这是换存储后端的升级路径，出问题的表现是"以前的图全裂了"且不自愈 |
| 不存在的 sha 回 **404** 而不是 500 | 客户端要靠状态码区分"对端也没有"和"服务端出错了" |

## 它**没**验什么（别当成验过）

- **真实云厂商的桶**：AWS / R2 / B2 的权限模型、区域、限流、分片上传一个都没碰过。
- **桶被外部删掉 / 换了一个桶**之后的行为。
- **两台客户端同时上传同一个键**的竞态。内容是同一份、键是内容的哈希，所以理论上
  无害（谁先谁后都是同一个对象），但没有实测。
- **大文件**：单次 PUT 的路径是走通了，但只有几十字节的负载。
